# vault-doctor · 笔记库结构体检 Agent

一个用 Python + LLM 工具调用（tool calling）实现的小 Agent，用来体检 Obsidian 笔记库的结构，并自动生成一张**真实反映笔记之间关系**的知识地图。

---

## 它解决什么问题

我的 Obsidian 笔记库有 21 篇笔记，靠一套**手工维护**的索引页串起来（一个根索引 + 4 个分组页）。问题出在同步上：

- 根索引里那张 mermaid 知识图**只有 5 个节点**，而库里实际有 21 篇笔记、几十条前置依赖——**图和真实结构差了 4 倍**。
- 每新增一篇笔记，要手工改三个地方：根索引的 mermaid 图、分组页的笔记列表、分组页的学习顺序。三处手工同步，必然漏。
- 结果：库里出现了**2 篇孤儿笔记**。其中一篇是 0 字空文件，另一篇有 8131 字正文、却没有任何索引页收录它。

我原本用的插件已经能很好地完成"对话 + 检索笔记"。但它一次只看得见**一页**——**没有任何环节负责抬头看一眼全局**。

所以我做的不是再一次检索，而是补上缺掉的那一步：**通读全库，再汇总成图。**

---

## 它做什么

一次运行，自动完成：

1. **全库扫描** —— 遍历所有 `.md`，解析 `[[双链]]`，统计字数
2. **结构体检** —— 找出孤儿笔记、断链、空文件
3. **读索引页** —— 从各分组页表格的「前置」列里，提取真实的依赖关系
4. **生成知识地图** —— 汇总成一张 mermaid 图，实线是已有链接，虚线是建议新增的归属
5. **落盘** —— 写入 `vault/_auto/`，**绝不覆盖任何现有笔记**

## 它是怎么工作的

一个标准的 tool-calling 循环：

```
用户提问
   ↓
把消息 + 工具清单发给模型
   ↓
模型自主决定调用哪个工具（可能一次调好几个）
   ↓
本地执行工具，结果作为 role="tool" 的消息回灌
   ↓
模型拿着结果再决定一次 …… 直到它不再需要工具
   ↓
输出最终结果
```

**三个工具：**

| 工具                            | 类型   | 作用                     |
| ----------------------------- | ---- | ---------------------- |
| `scan_vault()`                | 确定性  | 全库扫描，返回结构快照            |
| `read_note(title)`            | 确定性  | 读单篇笔记全文                |
| `write_report(name, content)` | 有副作用 | 写入产物（限定在 `_auto/` 目录内） |

## 一个对照实验：约束强度 vs 输出质量

这个项目里我认为最有价值的一部分，是一个只改了**一个变量**的对照实验。

### 设置

任务、工具、输出结构、铁律，**全部相同**。唯一的差异是 system prompt 的约束强度：

|     | 限定步骤版（`PROMPT_STRICT`）                                | 只给目标版（`PROMPT_LOOSE`）       |
| --- | ----------------------------------------------------- | --------------------------- |
| 步骤  | 明确列出 3 步：先 scan_vault → 再 read_note → 最后 write_report | **不写**，只加一句"先做什么、用几轮，你自己决定" |
| 线索  | 告诉它"依赖关系藏在索引页表格的『前置』列"                                | **不给**，让它自己找                |
| 语气  | "工作流程是固定的，不要自由发挥"                                     | 无                           |

切换方式：改文件顶部的 `PROMPT_MODE = "strict" | "loose"`。

### 数据

| 观察点       | 限定步骤版           | 只给目标版           |
| --------- | --------------- | --------------- |
| 第 1 轮     | `scan_vault`    | `scan_vault`    |
| 消息条数轨迹    | 2 → 4 → 10 → 12 | 2 → 4 → 10 → 12 |
| 第 2 轮读了几篇 | 5 篇，一轮并列读完      | 5 篇，一轮并列读完      |
| 读的是哪几篇    | 那 5 个索引页        | 同样那 5 个索引页      |
| 总轮数       | 4               | 4               |
| 是否写出文件    | 是               | 是               |

**过程零差异。**

### 结论

**松绑没有改变它"怎么做"，只改变了它"怎么说"。**

输出侧的差异：

- 限定版用嵌套小圆点列孤儿笔记；只给目标版换成了**四列表格**（笔记 / 字数 / 应归入 / 理由），可扫读性明显更好
- 限定版没有收尾观察；只给目标版主动补了一段整体健康度评价
- 对同一篇笔记（`C++ 分层算法练习题`）的归类判断，只给目标版更准确

### 我猜错的地方

我原本以为原因是"约束压窄了它的信息面"——**数据推翻了这个猜测**，两版读的是完全相同的 5 篇索引页。

真正的原因是：那句"**不要自由发挥**"本意只想管**步骤**，但它的副作用**溢出了**——连**表达**一起压住了。 

那么，过程为什么纹丝不动？因为**工具自身的 `description` 里还拽着引导**，比如 `scan_vault` 的描述写着"任何关于笔记库结构的任务，**都必须先调用它**"。

### 由此得到的两条启示

1. **一句约束的副作用，会溢出到它没打算管的地方。** 写 prompt 时，"我不想让你做 X" 很可能变成 "你连 Y 也别做了"。
2. **提示词无法真正"清空"引导——每一个 `description` 都在下指令。** 想让 Agent 自主多少，不能只看 system prompt。

> ⚠️ 样本量说明：目前 n=1 vs n=1。结论方向明确，但还没做多次重复验证。

## 两个设计决定

### 一、代码做确定的事，模型做需要判断的事

工具不是越多越好，而是要把职责切开：

| 交给代码（确定性）     | 交给模型（语义判断）                      |
| ------------- | ------------------------------- |
| 遍历目录、解析双链、数字数 | 这篇孤儿笔记该归到哪个分组                   |
| 统计孤儿和断链       | 两篇笔记谁是前置                        |
| 拼装 mermaid 语法 | 「Rule of Five」和「构造函数与析构函数」是什么关系 |

**脚本会数数，但脚本不认识 `Rule of Five` 是那五个特殊成员函数。** 这条边界划在哪，决定了 Agent 是聪明还是笨。

### 二、锁死"输出格式"，但不要锁死"步骤"

这个区分正是上面那个实验的产物：

- **格式要锁死** —— 产物必须是「结构体检 / 知识地图 / 建议」三节，章节一个不多一个不少。否则每次跑出来结构都不一样，没法用。
- **步骤不要锁** —— 一旦规定"先做 A 再做 B"，它会连表达一起变保守。

**约束该加在"要什么"上，不该加在"怎么做"上。**

## 踩过的坑

**`UnicodeEncodeError: 'ascii' codec can't encode characters in position 10-16`**

第一次运行时，API Key 用的还是占位符 `sk-在这里粘贴你的key`。那 7 个中文字符被塞进了 HTTP 请求头，而请求头只能放 ASCII。

定位过程比错误本身有意思：报错里的 `position 10-16` 指向的是 `Bearer sk-在这里粘贴你的key` 这个字符串——数一下，`B` 是第 0 位，第 10 位正好是"在"。**报错信息给的不是谜语，是地址。**

**另一个坑：`call.function.arguments` 是 JSON 字符串，不是字典。**

直接当字典用会炸，必须先 `json.loads()`。

## 已知局限

- `scan_vault()` 把全库结构一次性塞给模型，笔记规模再大就会超出上下文。**真正的解法是分级检索**（先给目录，让模型按需深入）。
- 双链解析用的是正则，没处理 `![[嵌入]]`、`[[链接|别名]]`、`^blockid` 等 Obsidian 高级语法。
- 写入位置硬编码在 `_auto/`，是安全考虑，但不够灵活。
- 目前只处理单库，不支持多 vault。

## 学到什么

- **模型没有记忆。** 每一轮都要把完整对话重新发过去。它"记得什么"，完全取决于你塞回去了什么。
- **`description` 不是注释。** 注释是给人看的，`description` 是写给**模型**看的接口说明。它写得含糊，模型就判断不准。
- **模型可以"边说边举手"。** 它调用工具时，`content` 字段往往不是空的，会有类似 "I'll search your notes" 的话。只处理 `tool_calls` 而丢掉 `content`，就丢了它的思考过程。
- **错误信息也是写给模型的。** 工具执行失败时返回一句"未知工具：xxx"而不是抛异常，模型看到会自己改对——**把错误变成模型可读的反馈，比让程序崩溃正确得多。**
