# vault-doctor · 笔记库结构体检 Agent

一个用 Python + DeepSeek API 实现的最小 Agent，用来体检我的 Obsidian 笔记库结构，并自动生成一张**真实反映笔记关系**的知识地图。

---

## 为什么做这个

我的 Obsidian 笔记库有 21 篇笔记，靠一套手工维护的索引页串起来（一个根索引 + 4 个分组页）。问题出在**同步**上：

- 根索引里的 mermaid 知识图**只有 5 个节点**，而库里实际有 21 篇笔记、几十条前置依赖——地图和真实结构差了 4 倍。
- 每新增一篇笔记，要手工改三个地方：根索引的 mermaid 图、分组页的笔记列表表格、分组页的学习顺序树。三处手工同步，必然漏。
- 结果：**2 篇笔记成了孤儿**。其中 `C++ Rule of Five 详解` 是个 0 字空文件，`C++ 分层算法练习题` 有 8131 字正文，却没有任何索引页收录它。

我原本用的 Obsidian 插件已经能很好地完成"对话 + 检索笔记"。但它一次只看得见**一页**——**没有任何环节负责抬头看一眼全局**。所以我做的不是再一次检索，而是补上缺掉的那一步：**通读全库，再汇总成图**。

## 它做什么

一次运行，自动完成：

1. **全库扫描** —— 遍历所有 `.md`，解析 `[[双链]]`，统计字数
2. **结构体检** —— 找出孤儿笔记、断链、空文件
3. **读索引页** —— 从各分组页表格的「前置」列里提取真实的依赖关系
4. **生成知识地图** —— 汇总成一张 mermaid 图，实线是已有依赖，虚线是建议新增的归属
5. **落盘** —— 写入 `vault/_auto/`，**绝不覆盖任何现有笔记**

## 它是怎么工作的

一个标准的 tool-calling 循环：

```
用户提问
   ↓
把消息 + 工具清单发给模型
   ↓
模型自主决定调用哪个工具（可能一次调好几个）
   ↓
本地执行工具，结果作为 role="tool" 的消息回灌
   ↓
模型拿着结果再决定一次 …… 直到它不再需要工具
   ↓
输出最终结果
```

**工具清单：**

| 工具                            | 类型   | 作用                     |
| ----------------------------- | ---- | ---------------------- |
| `scan_vault()`                | 确定性  | 全库扫描，返回结构快照            |
| `read_note(title)`            | 确定性  | 读单篇笔记全文                |
| `write_report(name, content)` | 有副作用 | 写入产物（限定在 `_auto/` 目录内） |

## 一个设计决定：代码做确定的事，模型做需要判断的事

这是我在这个项目里最主要的收获。工具不是越多越好，而是**要把职责切开**：

| 交给代码（确定性）     | 交给模型（语义判断）                      |
| ------------- | ------------------------------- |
| 遍历目录、解析双链、数字数 | 这篇孤儿笔记该归到哪个分组                   |
| 统计孤儿和断链       | 两篇笔记谁是前置                        |
| 拼装 mermaid 语法 | 「Rule of Five」和「构造函数与析构函数」是什么关系 |

脚本会数数，但脚本不认识 `Rule of Five` 是那五个特殊成员函数。**这条边界划在哪，决定了 Agent 是聪明还是笨。**

## 另一个决定：用固定输出契约取代"自由发挥"

模型写文档很容易每篇一个样。我在 system prompt 里把产物的章节结构**写死了**：

```
## 一、结构体检   ## 二、知识地图   ## 三、建议
```

章节一个不多一个不少。**把"你想要什么"变成固定的契约，模型就没得发挥了。**

## 怎么跑

```bash
pip install openai          # DeepSeek 兼容 OpenAI 接口，所以用官方 SDK 就行
python vault_doctor.py
```

`config.py` 里填两样东西：DeepSeek 的 API Key、Obsidian vault 的路径。

> 注意：`config.py` 含密钥，已在 `.gitignore` 中排除，不要提交。

## 关于 DeepSeek

DeepSeek 的接口**完全兼容 OpenAI 格式**，所以只需要改两个地方：

```python
client = OpenAI(api_key=KEY, base_url="https://api.deepseek.com")
#                                 ↑ 只有这里和调 OpenAI 不一样
```

## 已知局限

- `scan_vault()` 把全库结构一次性塞给模型，笔记规模再大就会超出上下文。**真正的解法是分级检索**（先给目录，让模型按需深入），这是我下一步要改的。
- 双链解析用的是正则，没有处理 `[[链接|别名]]` 之外的 Obsidian 高级语法（嵌入 `![[...]]`、块引用 `^blockid`）。
- 写入位置硬编码在 `_auto/`，是个安全考虑，但不够灵活。

## 踩过的坑

**`UnicodeEncodeError: 'ascii' codec can't encode characters in position 10-16`**

第一次运行时，API Key 用的是占位符 `sk-在这里粘贴你的key`。那 7 个中文字符被塞进了 HTTP 请求头，而请求头只能放 ASCII，于是报错。

有意思的是定位过程：报错里的 `position 10-16` 指向的是 `Bearer sk-在这里粘贴你的key` 这个字符串——数一下，`B` 是第 0 位，第 10 位正好是"在"，第 16 位正好是"的"。**报错信息给的不是谜语，是地址。** 从那以后我学会了先看位置，再猜原因。

另一个细节：`call.function.arguments` 拿到的是 **JSON 字符串**，不是字典。直接当字典用会炸，必须先 `json.loads()`。这个坑在实现工具调用时几乎人人会踩。

## 学到了什么

- 模型**没有记忆**。每一轮都要把完整对话重新发过去。它"记得什么"，完全取决于我塞回去了什么。
- `description` 不是注释。注释是给人看的，`description` 是写给**模型**看的接口说明。它写得含糊，模型就判断不准。
- **模型可以"边说边举手"**：它调用工具时，`content` 字段往往不是空的，会有类似 "I'll search your notes" 的话。只处理 `tool_calls` 而丢掉 `content`，就丢了它的思考过程。
- **错误信息也是给人（模型）看的**。工具执行失败时返回一句"未知工具：xxx"而不是抛异常，模型看到会自己改对——把错误变成模型可读的反馈，比让程序崩溃正确得多。
